# Execution notes

A mathematically equivalent sparse graph-closure implementation replaced redundant whole-catalog training computations after initial timing trials, before test access. Each training batch computes only the item nodes needed by its histories, candidates and auxiliary prefixes, plus the exact original two-hop neighbor closure. Full evaluation still uses the complete graph and eligible catalog. Dense and sparse scores and parameter gradients agree within 3e-8 on checked model variants. This changes computation, not architecture, examples, loss or search budget. CPU thread count reduced from4 to1 to reduce overhead. Completed dense tuning trials remain in the record; interrupted incomplete trials restart deterministically. Source hashes identify each execution version. The protocol is a local dated plan, not external preregistration.

The first three Amazon ranking-only tuning trials used the dense four-thread executor. Their exact source has been retained as source/study_dense_original.py and its SHA256 matches the hash recorded in those three runs. All other completed fitting runs use the sparse one-thread executor. The portable parallel driver preserves this distinction when rebuilding from scratch. Executor selection follows the original run provenance, never test outcomes.

The fixed item-neighborhood settings for both datasets were selected using validation before any test evaluation. The evaluator loads these frozen settings, and its global gate also creates any missing selections for both datasets before opening test evaluation. This makes the all-model selection barrier explicit without changing the neighborhood algorithm.
